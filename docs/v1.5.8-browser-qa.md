## Implemented behavior

- **#118:** Machine and Equipment keep separate PM sections and accordion state. Shared presentation groups assets into columns of ten, aligned left, with responsive wrapping. Cards are at most 400px wide. PM details wrap inside the card. Opening animates for 220ms; closing takes 190ms. The accent chevron rotates, keyboard focus remains visible, closed details are inert, and reduced motion disables transitions. PM calculations, task order, warning notes and actions are unchanged.
- **#119:** Inventory's cyan hover/focus surface is shared by data tables, including Requisitions, History and Vendors. The module-accent hover that caused amber requisition rows is removed. Pointer hover requires a fine pointer that supports hover; keyboard focus remains available on all devices. Selected staging rows have an explicit accessible selection state and retain the existing selected-row styling. Obsolete rows and status/priority badges keep their semantic colors.
- **#120:** Inventory Create/Edit includes the opt-in Dashboard Stock Alert checkbox. Dashboard loads a filtered endpoint, shows separate Out of Stock and Low Stock counters, and opens accessible modal lists. The quantity prompt suggests `max(minimum - quantity, 1)`, accepts positive numeric quantities under existing requisition rules, and submits through the existing staging bulk API. Users can choose an existing open batch; staging-only users without requisition viewing permission use the existing General batch fallback. Existing staging links open the matching batch and filtered part; requisition links open the active view filtered to that requisition. Inventory links open the matching part editor for authorized users or its filtered inventory row for viewers.
- **#121:** One compact requisition card contains three native buttons: Active, Requested and Ordered. Existing counts, view routing and refresh remain unchanged.

Inventory Attention refreshes on load, window focus, visibility return and every 10 seconds while visible, matching Inventory's existing cadence. It makes no full-catalog request and prevents overlapping refresh requests. Successful staging waits for any earlier read, then fetches committed state. A server-side guard on Dashboard-originated staging rejects existing requests across batches, including stale-popup submissions. The existing bulk staging behavior for other callers is preserved.

The legacy `orderPlaced` field means any active request in this repository. Inventory Attention resolves the existing requisition status first, so Requested is shown as **Requisition Added**, and Ordered as **Ordered**. Staged/requested/ordered parts remain visible until replenished, disabled or obsolete.

## Database migration and compatibility

The existing idempotent startup migration adds:

```sql
ALTER TABLE inventory_parts
ADD COLUMN dashboard_stock_alert_enabled INTEGER NOT NULL DEFAULT 0;
```

No existing data is removed or enabled. Fresh rows default to OFF. The API property is `dashboardStockAlertEnabled`. An older PATCH client that omits it preserves the stored setting. Inventory exports, Excel templates and focused JSON/CSV backups include **Dashboard Stock Alert** as Yes/No. Missing or blank import values resolve to OFF, including updates from legacy import files; explicit opt-in must be included to preserve enabled alerts through such an import. Invalid import boolean text is rejected.

Validation covers a legacy schema without the column, new defaults, enable/disable, quantity replenishment, obsolete exclusion, positive quantity validation, staging duplicates across batches, Requested versus Ordered, permissions, CSV/Excel round trips and an actual master database backup/restore. The database migration has been exercised only in isolated test/QA databases. Production has not been migrated.

## Local browser staging

After building, run `node scripts/stage-v1.5.8-qa.mjs`. It refuses an occupied port, binds to `127.0.0.1:4289`, creates a new timestamped folder under `tmp`, and seeds only synthetic QA data. It does not read production data. The script prints the fixture path, process ID and credentials-file location. An alternate unused port can be selected with `MCC_QA_PORT`.

The prepared review instance is **http://127.0.0.1:4289**, with sample data in `F:\MCC_V1_FINAL\tmp\v1.5.8-browser-qa-1788978642760`. Its `QA-ACCESS.txt` contains the generated local credentials, and `screenshots` contains desktop/mobile visual evidence.

Open the printed URL and use `QA-ACCESS.txt` inside that fixture for the local QA account. Each fixture includes `server.log` and `qa-instance.json`. Preserve its data, uploads, backups and recovery folders. To stop a QA instance, verify and stop only the process ID in its metadata.

Sample data includes 12 Machine assets and 12 Equipment assets with attention PMs, opt-in Out/Low parts, disabled/healthy/obsolete controls, and staged/requested/ordered parts. This is a review environment; its quantities and records are artificial.
